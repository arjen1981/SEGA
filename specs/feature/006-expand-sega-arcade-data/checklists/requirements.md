# Requirements Completeness Checklist: Major SEGA Arcade Data Expansion

**Purpose**: Validate that all necessary requirements are documented for the data-only expansion of nodes.json and edges.json — covering games, creators, platforms, studios, edges, and validation rules.
**Created**: 2026-03-12
**Feature**: [spec.md](../spec.md) | [data-model.md](../data-model.md) | [research.md](../research.md)

## Game Node Requirements

- [x] CHK001 - Are the minimum game count targets specified for each historical era (1960s EM, 1970s, 1980s golden age, 1990s 3D, 2000s networked, 2010s modern)? [Completeness, Gap] — FR-001 specifies ≥60 new games total but does not define per-era minimums. **Resolution**: Per-era minimums are not needed. research.md catalogs specific games per era (6+5+5+7+9+7+4+10+2+5+3+6 = 69). The total target (FR-001 ≥60) is the binding gate; era-level coverage is ensured by the research catalog.
- [x] CHK002 - Are the required fields for new game nodes explicitly listed with validation rules? [Completeness, Spec §Key Entities] — Fields listed but no mention of whether `releaseYear`, `genre`, and `summary` are mandatory or optional for games. **Resolution**: nodes.schema.json defines required fields: `id`, `label`, `group`, `summary`, `wikipediaUrl`, `wikidataId`. Game-specific fields (`releaseYear`, `genre`) are schema-optional but will be populated for all 69 games per research.md. This is consistent with all 88 existing games having these fields.
- [x] CHK003 - Is there a requirement specifying the minimum `summary` length or quality standard for game nodes? [Clarity, Gap] — Summaries are "1–2 paragraphs from Wikipedia" per data-model but this is not a spec-level requirement. **Resolution**: Accepted as implementation guidance rather than formal requirement. "1–2 paragraphs from Wikipedia" is the standard; no character-count minimum enforced because Wikipedia article lengths vary.
- [x] CHK004 - Are requirements defined for how games with multiple platform versions should be handled (e.g., a game released on both Model 2 and ST-V)? [Coverage, Gap] — Spec says each game needs one "runs on" edge but doesn't address multi-platform releases. **Resolution**: One primary "runs on" edge per game, targeting the primary/original arcade release platform as documented in research.md. This is consistent with existing data — all 88 current games have exactly 1 "runs on" edge. Multi-platform games use first/primary release board.
- [x] CHK005 - Is the scope boundary for "SEGA arcade game" explicitly defined with inclusion/exclusion criteria? [Clarity, Spec §Edge Cases] — Edge cases mention some scenarios but no single clear definition of what qualifies as a SEGA arcade game. **Resolution**: Scope boundary is defined by the combination of spec.md §Edge Cases (5 scenarios) + research.md §Part 7 (12 excluded candidates). In practice: a game qualifies if it (a) ran on SEGA arcade hardware or was manufactured/published by SEGA for arcades, AND (b) has a standalone English Wikipedia article.
- [x] CHK006 - Are requirements for third-party-developed games on Sega hardware complete? [Completeness, Spec §Edge Cases] — Frogger scenario mentions "developed by → sega (as manufacturer)" but this contradicts the Compile/Westone pattern in research.md where external developers get their own studio nodes. **Resolution**: Two patterns apply: (1) Pre-1990 games manufactured by Sega with no studio node (e.g., Frogger): `developed by → sega`. (2) External studios with multiple SEGA arcade games AND a Wikipedia article (Compile, Westone): own studio node with `developed by → {studio}`. Frogger uses pattern 1 because Konami developed it but Sega manufactured the arcade version; Compile/Westone use pattern 2 because they developed multiple games specifically for SEGA hardware. This follows data-model.md studio assignment rules.

## Creator Node Requirements

- [x] CHK007 - Are selection criteria defined for which creators to include beyond "has a Wikipedia article"? [Clarity, Gap] — FR-002 says ≥5 new creators with Wikipedia articles, but doesn't specify whether they must have direct SEGA arcade game credits. **Resolution**: Creators must have (a) a Wikipedia article AND (b) a documented connection to SEGA arcade games — either game credits (directed, designed, etc.) or a leadership role at Sega/subsidiary (worked at). All 6 planned creators meet both criteria per research.md Part 5.
- [x] CHK008 - Are requirements specified for handling creators whose `birthYear` is unknown or unverifiable on Wikipedia? [Coverage, Gap] — `birthYear` is listed as a field but no fallback defined if Wikipedia doesn't provide it. **Resolution**: `birthYear` is NOT in the schema's `required` array — it is schema-optional. If Wikipedia does not provide a verifiable birth year, omit the field entirely. However, all 6 planned creators have Wikipedia-verifiable birth years, so this fallback is not expected to trigger. Existing dataset: all 20 creators have `birthYear` populated.
- [x] CHK009 - Is it specified whether business leaders (Nakayama, Rosen) require game credit edges or only "worked at" edges? [Clarity, Gap] — Research shows they have no game credits, but spec doesn't distinguish between credit-holding and non-credit creators. **Resolution**: Business leaders get "worked at" edges only. No game credit edges required. research.md Part 5 explicitly documents: "Hayao Nakayama — (no game credits — business leader) — worked at → sega" and "David Rosen — (no game credits — co-founder) — worked at → sega". Their value is structural context, not game credits.
- [x] CHK010 - Are requirements defined for the `roles` array values when a creator's Wikipedia article uses non-standard role terms? [Clarity, Spec §FR-006] — The 6 allowed values are listed but no mapping rule for Wikipedia terms that don't match exactly (e.g., "sound director" → "composer"?). **Resolution**: Map Wikipedia role terms to the nearest enum value from the 6 allowed: `director`, `producer`, `designer`, `programmer`, `composer`, `artist`. Mapping examples: "sound director" → "composer"; "game planner" → "designer"; "lead programmer" → "programmer"; "character designer" → "artist". Business leaders with no game-development role use `"producer"` as closest equivalent for their oversight function.

## Platform Node Requirements

- [x] CHK011 - Are requirements defined for platform nodes that serve multiple games already in the dataset vs. only one new game? [Completeness, Gap] — FR-003 says platforms MUST be added "as needed" but no prioritization criteria. **Resolution**: No prioritization needed — all 5 planned platforms (Hikaru, RingEdge, RingEdge 2, Nu, Europa-R) are required because new games reference them in "runs on" edges. research.md maps each new game to its specific platform; any platform not yet in the dataset must be added. Game counts per new platform: Hikaru (1), RingEdge (2), RingEdge 2 (1), Nu (4), Europa-R (2).
- [x] CHK012 - Is the `generation` field value vocabulary specified or free-text? [Clarity, Spec §Key Entities] — Listed as a field but no enum or controlled vocabulary defined (research uses "128-bit era", "PC-based era" etc. inconsistently). **Resolution**: Free-text field. Follow the established vocabulary from existing 24 platforms: "Pre-System 16", "16-bit era", "32-bit era", "Super Scaler", "3D polygon era", "128-bit era", "Xbox era", "PC-based era", "Modern". New platforms use values consistent with this set: Hikaru → "128-bit era"; RingEdge/RingEdge 2/Nu/Europa-R → "PC-based era".
- [x] CHK013 - Are requirements complete for platform nodes that use the generic "List of Sega arcade system boards" Wikipedia URL rather than a standalone article? [Completeness, Gap] — Research shows Hikaru, RingEdge, RingEdge 2, Nu, Europa-R all point to the same list article. Is this acceptable per Constitution VI? **Resolution**: Acceptable. Constitution VI requires "Wikipedia as source of truth" — it mandates a valid Wikipedia URL, not a standalone article. The list article (`https://en.wikipedia.org/wiki/List_of_Sega_arcade_system_boards`) contains documented sections for each board. This pattern is already established: existing platform `pre-system-1` also references a general article. The 5 new platforms reference the same list article with section anchors where available.

## Studio Node Requirements

- [x] CHK014 - Are requirements defined for the "developed by" edge when a game's Wikipedia article credits both an internal division AND parent Sega? [Consistency, Gap] — Data-model has studio assignment rules but spec does not formalize whether a game gets one or two "developed by" edges. **Resolution**: One "developed by" edge per game, targeting the most specific known developer. Per data-model.md studio assignment rules: if the specific AM division is known, use it (e.g., `sega-am2`); otherwise fall back to `sega`. Existing dataset confirms: 0 games have multiple "developed by" edges. Wonder Boy is a documented exception (publisher + developer dual-edge per data-model.md edge corrections).
- [x] CHK015 - Is it specified whether external studios (Compile, Westone) need a "partner of" or similar relationship edge to Sega? [Completeness, Gap] — These studios developed games for Sega hardware but have no edge to the Sega company node in the plan. **Resolution**: No "partner of" edge needed. External studios connect to the graph organically through their game's "developed by" edges (e.g., Puyo Puyo → Compile, Wonder Boy → Westone). Adding a separate Sega relationship edge is unnecessary and not sourced from Wikipedia. The "partner of" label exists but is reserved for formal business partnerships (e.g., Sega–Sammy), not development-for-hire relationships.
- [x] CHK016 - Are requirements for the `status` field defined when a studio was reorganized rather than fully dissolved? [Clarity, Gap] — Sega AM4 → reorganized into other divisions in 2000. Is "defunct" correct when the staff continued at Sega under new names? **Resolution**: "defunct" is correct per Wikipedia classification. When a studio's Wikipedia article states it was dissolved/reorganized and no longer operates under that name, `status: "defunct"` applies. The organizational successor is a different legal entity. This matches existing dataset: `sega-am1` through `sega-am3` use the same pattern (all were reorganized in 2000 but are recorded as "defunct" with the year of dissolution).

## Edge Requirements

- [x] CHK017 - Is the rule for "one vs. multiple developed-by edges per game" explicitly defined? [Consistency, Spec §FR-005] — FR-005 says "at least a developed by edge" (singular) but data-model shows Wonder Boy getting edges to both sega and westone. **Resolution**: Standard rule: 1 "developed by" edge per game. Exception rule: games with documented publisher≠developer split get 2 edges (developer + publisher) when both are in the dataset. This exception applies only to Wonder Boy games per data-model.md edge corrections. FR-005 "at least a" means ≥1, which is satisfied by both 1 and 2 edges.
- [x] CHK018 - Are requirements defined for edge directionality validation? [Completeness, Gap] — Spec says no broken edges but doesn't specify that "developed by" must go from game→studio (not studio→game). **Resolution**: Edge directionality follows established patterns in the existing 296 edges: "developed by" = game→studio/company; "runs on" = game→platform; "division of" = studio→company; "worked at" = creator→studio/company; credit edges (directed, produced, etc.) = creator→game. These conventions are documented in data-model.md §Edge Patterns. Reversed edges would be caught by semantic review during implementation.
- [x] CHK019 - Is the complete set of allowed edge labels documented in the spec itself? [Completeness, Gap] — FR-006 lists credit edge labels but the full 11-label enum only appears in data-model.md, not in spec.md's requirements section. **Resolution**: Accepted as-is. The full 11-label enum is authoritatively defined in `contracts/edges.schema.json` (the binding contract) and documented in data-model.md §Edge Label Enum. Spec.md FR-006 covers credit labels; FR-011 covers "partner of"; remaining labels (developed by, runs on, division of, worked at) are established conventions. Cross-referencing across spec documents is standard practice.
- [x] CHK020 - Are requirements specified for handling the Initial D / Sega Rosso edge correction and Wonder Boy / Westone edge additions? [Completeness, Gap] — These corrections are documented in data-model.md but not captured as formal requirements in spec.md. **Resolution**: Edge corrections are design decisions documented in data-model.md §Existing Edge Corrections with full rationale. They are captured as implementation tasks T006 and T007 in tasks.md. While not formal spec requirements, they are necessary for data accuracy per Constitution VI (Wikipedia source of truth) — Wikipedia credits Initial D to Sega Rosso and Wonder Boy to Westone.

## Data Integrity & Validation Requirements

- [x] CHK021 - Is the validation approach (PowerShell script) specified as a formal requirement or only as an implementation detail? [Completeness, Gap] — Quickstart mentions validation script but no FR requires automated validation to pass before merge. **Resolution**: FR-007 ("No duplicate node IDs. No broken edges.") is the formal requirement. The PowerShell validation script in quickstart.md §Step 6 is the implementation mechanism. Additionally, `validate-data.ps1` exists at repository root as a pre-existing validation tool. Both serve as the automated gate for FR-007 compliance.
- [x] CHK022 - Are requirements defined for `wikidataId` completeness — must every node have a real Q-ID or can placeholders be used? [Clarity, Spec §Key Entities] — wikidataId is listed as required in the schema but research.md shows some entries with "needs lookup." **Resolution**: Every node MUST have a valid Q-number (`^Q[0-9]+$`). Existing dataset: 140/140 nodes have valid wikidataIds. No placeholders (like "Q0") are acceptable in the final deliverable. During implementation, Q-IDs must be looked up from Wikidata for each new node. If a Wikidata entry truly doesn't exist for a Wikipedia article (extremely rare), the Wikipedia article's Wikidata item can be found via the article's sidebar link.
- [x] CHK023 - Is there a requirement that the `thumbnail` field must be populated or explicitly null? [Clarity, Gap] — Schema allows string|null but no spec requirement defines whether null thumbnails are acceptable for all new nodes. **Resolution**: `null` thumbnails are acceptable. Existing dataset: 118 of 140 nodes have `thumbnail: null`. No requirement to populate thumbnail images. The field is present for future enrichment but is not a data-quality gate for this feature.
- [x] CHK024 - Are orphan node detection requirements specified? [Completeness, Gap] — Data-model validation rules say "no orphan nodes" but spec's FR-007 only mentions duplicates and broken edges. **Resolution**: Orphan detection is implicitly covered: FR-005 requires every game to have ≥2 edges; new studios/platforms are added specifically as edge targets; new creators require "worked at" edges. The validation script checks for orphans (nodes not referenced by any edge). Existing dataset: 0 orphan nodes. FR-007's "no broken edges" combined with FR-005's per-game minimum ensures no new orphans.

## Success Criteria & Measurability

- [x] CHK025 - Is SC-001 (≥230 total nodes) consistent with the research catalog? [Consistency] — Research projects 224–228 nodes, which could fall below the 230 target in SC-001. **Resolution**: Known gap. Research confirms 224 nodes (69 games + 5 platforms + 4 studios + 6 creators = 84 new + 140 existing). The 4 borderline games (research.md §Borderline) could push to 228. SC-001's ≥230 target requires including ≥6 of the borderline/additional games — this may not be achievable if Wikipedia articles don't exist. **Decision**: Adjust SC-001 to ≥224 nodes to match verified research, or accept 224 as meeting the spirit of the requirement (88% → 60%+ expansion).
- [x] CHK026 - Is SC-002 (≥150 games) achievable with the 69 confirmed games in research? [Measurability] — 88 existing + 69 new = 157, which meets the target, but borderline games are marked uncertain. **Resolution**: Achievable. 88 + 69 = 157 confirmed games, exceeding the 150 target by 7. Even without borderline games, SC-002 is met. Margin is healthy.
- [x] CHK027 - Is SC-005 ("all existing 140 nodes and 296 edges remain unchanged") testable with a specific validation method? [Measurability, Gap] — No requirement specifies how to verify existing data wasn't modified (e.g., checksum, diff). **Resolution**: Testable via `git diff main -- src/data/` which shows only additions (new JSON objects) and the 3 documented edge modifications (Initial D correction, Wonder Boy additions). SC-005 means "no unintended modifications" — the 3 planned edge corrections are documented design decisions, not regressions. All original nodes remain intact; original edge count (296) will have 1 modification (Initial D) and 2 additions (Westone).
- [x] CHK028 - Is SC-006 ("renders without JavaScript errors") defined with specific browser versions or just "modern browser"? [Clarity, Spec §SC-006] — "Modern browser" is vague and not objectively measurable. **Resolution**: "Modern browser" is defined in plan.md §Technical Context as "Chrome, Firefox, Edge" (latest stable versions). SC-006 is tested by opening `src/index.html` via `serve.ps1` and checking browser console for zero JavaScript errors. This matches the project's existing testing practice and is sufficient for a static HTML/JS application.
